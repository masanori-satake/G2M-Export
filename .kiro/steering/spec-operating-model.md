# Spec 運用モデル

仕様駆動開発の進め方を定義する。

---

## フロー概要

```
Requirements（要件定義）→ Design（技術設計）→ Tasks（実装タスク）→ 実装 → レビュー
```

## 各フェーズの目的

### Requirements（要件定義）

- 「何を実現するか」を定義する
- ユーザーストーリーと受け入れ基準を明確にする
- 正しさの性質（Correctness Properties）を特定する
- スコープ外を明示する

### Design（技術設計）

- 「どう実現するか」を定義する
- 既存コードへの影響範囲を特定する
- データフロー・モジュール間の依存関係を整理する
- エッジケースと制約を洗い出す

### Tasks（実装タスク）

- 実装の順序と粒度を決める
- 各タスクの完了条件を明確にする
- テスト方針を含める
- 依存関係を可視化する

## レビュー観点

### Requirements レビュー

- 受け入れ基準は検証可能か？
- スコープは適切か？（大きすぎ/小さすぎないか）
- 既存機能との整合性はあるか？
- Open Questions は残っていないか？

### Design レビュー

- 既存アーキテクチャとの整合性
- AGENTS.md の制約（git コマンド非依存、日本語コメント等）を満たすか
- 将来の拡張性を考慮しているか
- テスト容易性

### Tasks レビュー

- タスクの粒度は1つのPRに収まるか
- 依存関係は正しいか
- テスト項目は網羅的か

## 承認の考え方

- 各フェーズの成果物はユーザーの承認を得てから次に進む
- 「完璧」を求めず「十分に明確」であれば承認とする
- 承認後に判明した問題は、追加の Spec または Open Questions として扱う
- 実装中に設計変更が必要になった場合は、Design に立ち戻って更新する
