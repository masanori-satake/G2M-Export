# 移行原則（Migration Principles）

今後の開発における基本方針を定義する。

---

## Spec 必須ルール

- 新機能追加・既存機能の変更は、必ず Spec（requirements → design → tasks）を経てから実装する
- Spec なしで直接コードを変更してよいケース:
  - typo 修正
  - リンター指摘への対応
  - ドキュメントの軽微な修正
  - テストの追加（既存仕様の範囲内）
- 判断に迷う場合は Spec を作成する側に倒す

## 既存コードの扱い方

- 既存コードは「動作する実装」として尊重する
- リファクタリングは Spec を通じて計画的に行う（衝動的な書き換えを避ける）
- 既存の振る舞いを変更する場合は、まず現状の振る舞いをテストで固定する
- AGENTS.md に記載のルール（エラーメッセージ構成、日本語コメント等）は引き続き遵守する

## 曖昧仕様への対応方針

- 「事実」「推定」「不明」を明確に区別する
- 曖昧な部分は Open Questions として記録し、無理に確定させない
- 実装を進める際に曖昧さに遭遇したら:
  1. legacy-system-overview.md に追記する
  2. ユーザーに確認する
  3. 確認結果を Spec に反映する

## Vibe セッションと Spec セッションの使い分け

| ユースケース | セッション種別 |
|---|---|
| 調査・質問・方針相談 | Vibe |
| コードの読み解き・理解 | Vibe |
| 新機能の設計・実装 | Spec |
| バグ修正（影響範囲が明確） | Spec |
| typo・リンター修正 | Vibe |
| リファクタリング | Spec |
| ドキュメント更新のみ | Vibe |
